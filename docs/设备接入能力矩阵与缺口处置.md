# 设备接入能力矩阵与缺口处置

> **用途**：一台摄像机（枪机）接入平台后，按行业规范应有哪九项能力 —— 三个接入协议各怎么做、差异在哪、**我们实现了哪些**、
> **缺的部分该由谁补**（依赖库/SDK 没提供 → 换库或自研；SDK 提供了我们没接 → 我们必须实现）。
>
> **本文只回答"能力面"，不涉及页面与交互设计。** 页面统一见各接入页与 `views/common/CommonChannelEdit.vue`。
>
> 编写日期：2026-11-24

### 0.2 三条判读口径（不说清会读歪矩阵）

1. **GB/T 28181 没有"设备符合性/一致性"专章**（全文检索"一致性要求/符合性/检验"无正文命中）。
   因此**不存在"摄像机必须实现 N 项功能"的清单**。强制面只有两处：第 7 章的 **应/宜**，以及附录 A Schema 中每个元素的 **(必选)/(可选)**（附录 A 为规范性附录）。
   注意第 7 章主语大多是**"联网系统"**，不是"每台摄像机"。
2. **ONVIF 没有"必须实现"清单**，能力靠设备 `GetCapabilities`/`GetServices` 自描述。Profile S 是 IP 视频流最低画像，Profile G 才管录像回放。
3. **海康 SDK 头文件不承诺业务语义**。"枪机调 PTZ 返回什么错误码"这类问题头文件不作答（840 个 API 已逐个查证）。
   唯一可信来源是登录后 `NET_DVR_GetDeviceAbility(DEVICE_ABILITY_INFO)` 返回的能力集 XML。

> 附录编号在 2016→2022 之间**发生过重排**（如编码规则 2016 附录 D → 2022 附录 E；SDP 2016 F → 2022 G；保活 2016 M → 2022 K）。引用时务必按版本对号。

### 1.1 报警订阅：GB 的两套机制必须分清

| | 即时「报警事件通知和分发」（9.4） | 「事件订阅/通知」（9.11） |
|---|---|---|
| 强制性 | 7.4「**应能**实时接收报警源发送来的报警信息」 | 7.11「**宜**支持订阅和通知机制」 |
| 是否需先订阅 | **不需要**，设备产生报警即发 `MESSAGE` | 需先 `SUBSCRIBE` |
| 承载 | `MESSAGE` + `Notify/CmdType=Alarm` | `SUBSCRIBE` + `NOTIFY` |
| 订阅有效期 | — | 正文未规定；仅附录 P/N 域间目录订阅给默认 **600s** |
| 设备离线是否使订阅失效 | — | **规范无此条款**。订阅只由「过期未续订」「Expire=0 取消」「被订阅方发 terminated」三条路径清除 |
| 关键约束 | 2022 A.2.5.3 注：设备发 Method=2 设备报警后，**平台须先执行报警复位控制，设备才会发下一条** | 订阅方向是"观察者→事件源"，事件源可以是 SIP 服务器，不限于设备 |

## 3. 缺口归类与处置

> **判定原则**：缺口归属只看一件事 —— **依赖方（库 / SDK / 协议）到底有没有提供这个能力**。
> 提供了而我们没接 → **B 类，我们自己实现**；没提供 → **A 类，换库或自研，实在不行就接受**；我们做错了 → **C 类，修正**。

### 3.1 A 类：依赖方根本没提供（换库 / 自研 / 接受）

| 缺口 | 依赖方证据 | 处置 |
|---|---|---|
| **ONVIF 回放 / 录像检索** | `3rdpart/onvif-go` 全库检索 `GetReplayUri` / `FindRecordings` / `RecordingSearch` **0 命中** → 库不含 Profile G | **自研，不换库**。库的 `internal/soap/soap.go:105` 已是通用 SOAP 调用层（含 WS-Security），只需补 `Replay`（`GetReplayUri`）与 `RecordingSearch`（`FindRecordings` / `GetRecordingSearchResults` / `EndSearch`）合计 4 个操作的结构体，走同一个 `Call()`。换库收益低于自研成本 |
| **ONVIF Push 事件 / TopicSet** | 库仅有 PullPoint，无 Push 订阅；`GetEventProperties` 存在但设备常回不全，topic 需硬编码 | **接受**。用 PullPoint 已足够（事件拉取改为平台侧轮询），不追求 Push |
| **插件侧 MQTT** | SDK 头文件全包 grep `MQTT` **无任何接口**（MQTT 属设备侧能力，与 SDK 无关） | **不适用**。插件的事件出口是 MQTT，但入口靠 ISAPI alertStream / SDK 布防，无需 SDK 级 MQTT |
| **海康历史报警检索** | `NET_DVR_ALARM_SEARCH_COND/RESULT` 结构存在（51250-51295），但**无配套检索 API**（grep `AlarmSearch` 0 命中） | **接受**。历史报警靠平台侧 `zws_event` 留存，不回查设备 |
| **海康 `NET_DVR_RealPlay_V50` / `SetPTZAbsoluteEx`** | 头文件（linux64 + Win64 两版）**均 0 命中** | **不调用**。实时预览用 `_V40`；绝对定位用 `NET_DVR_SET_PTZPOS=292`（2268） |
| **GB 2022 `a=streamnumber` 子码流语法** | 协议有（2022 附录 G），我们的 `internal/gbsip` 与 `3rdpart/gb28181-go` 均无 | **自研**（我方协议栈，无第三方依赖）。2016 环境只能靠 `f=` 分辨率区分，能力天然受限 |

| 问题 | 位置 | 影响 | 修正 |
|---|---|---|---|
| **固定枪机被标成"有云台"** | `infrastructure/persistence/asset_backfill.go:774` `channelCaps()`：`if ptzType > 0 { 加 ptz }` | 规范里 **PTZType=3 是固定枪机、4 是遥控枪机，两者都没有云台**。枪机上报 3 就得到 `ptz` 能力位，界面云台按钮亮着，命令发下去不动作。**GB 的云台控制是无应答命令**，连错误都收不到 → 表现为"点了没反应且无任何提示" | 判定改为 `ptzType == 1 || ptzType == 2 || ptzType == 5`（球机/半球/遥控半球）才给 `ptz`；3/4 不给。2022 的 6/7 为多目全景/分割通道，需按机型另行判定 |
| **`plugin.yaml` 声明了未实现的能力** | `tools/hik-ipc-plugin/plugin.yaml` 的 `capabilities` 含 `playback`/`record_query`/`config`，实际无对应 RPC | 平台据此点亮 UI，用户点下去空转 | 要么补齐实现（见 §3.2），要么先从清单移除，**不能声明了不实现** |

## 4. 落到「枪机 / 未开录像 / 事件已开 / 插件已拿到事件」

**今天真能跑通的**：预览（插件主码流 RTSP）、通道列表与通道号、事件（alertStream 链路已通，**独立于 SDK 布防**，所以 `bySubScription` 那些坑在这条路径上不生效）、通道属性编辑。

**三个"看起来对、实际不对"的点**：

1. **PTZ 能力被误标** → C 类，见 §3.3 第 1 条。这是当前唯一会**误导用户操作**的错误。
2. **回放按钮语义** → 设备没开录像**完全合规**：规范从未强制设备必须录像（`DeviceStatus.Record` 是可选字段；7.7 那项「应」的主语是联网系统不是摄像机）。
   - GB 侧正确表现：`RecordInfo` 回 `SumNum=0` 不带记录列表（我们这条是对的，UI 应显示"无录像"而非报错）；
   - 海康侧正确表现：`FindNextFile` 回 **1001/1003**，且**不是异常**；
   - 现状问题：插件通道**根本没实现回放**，按钮点下去空转。
3. **ONVIF 通道永远不会有告警** → 我们没用 PullPoint。同一台枪机走 ONVIF 接入和走插件接入，告警能力是 0 与满的差别。

## 5. 优先级建议

| 优先级 | 事项 | 类别 | 理由 |
|---|---|---|---|
| **P0** | 修正 `channelCaps` 的 PTZType 判定 | C | 唯一"错功能"，会误导现场操作，改动 1 行 |
| **P0** | `plugin.yaml` 与实际实现对齐 | C | 声明了不实现，UI 空转 |
| **P1** | 插件回放 + 录像检索 | B | SDK 全有，只差实现；回放在 GB 7.8 是「应」，是接入闭环的硬需求 |
| **P1** | 插件子码流（`dwStreamType=1`） | B | 成本极小，直接提升带宽适应性 |
| **P1** | ONVIF 事件 PullPoint | B | 库完整支持；不做则 ONVIF 接入的设备零告警 |
| **P2** | 插件 PTZ/对讲/抓图能力集判定 | B | 让能力位来自设备自述而非猜测 |
| **P2** | GB 通道类型字段（`itemType` 等） | B | 补齐后可按 132/137 区分视频通道与语音输出通道 |
| **P3** | GB 2022 `a=streamnumber` 子码流 | A（自研） | 2016 环境收益有限，2022 设备普及后再做 |
| **P3** | ONVIF 回放（自研 Replay/RecordingSearch） | A（自研） | 复用 `internal/soap`，成本可控，但 ONVIF 接入目前不承载回放场景 |
