# 设备能力声明与自定义扩展设计

> 目标：把"平台固化的那批能力"和"驱动开发者自定义的能力/事件"统一到同一套模型。
> 平台只负责 **声明登记 → 鉴权/审计 → 透传 → 能力表/fuse → 信封+内码**；能力的**语义完全由驱动决定**，新增能力/事件**不改平台代码**。
> 关联文档：[物联设备统一接入模型.md](物联设备统一接入模型.md)、[插件化设备接入.md](插件化设备接入.md)、[接口与鉴权规范.md](接口与鉴权规范.md)。

---

## 0. 已确认的决策

1. 自定义能力**单列**，与基线 `capabilities` **分开**：manifest 新增 `custom_capabilities`。
2. 自定义事件落 **`zws_custom_event` 通用表**，平台提供查询接口与「自定义事件」菜单。
3. **基线能力与自定义能力统一**：都走"声明 + 能力表 + fuse + 通用 UI 生成"；区别仅在**执行路径**——基线走强类型 driver，自定义走通用 `command` 透传。
4. **Agent 零改动**：`/plugins/{id}/*` 已是全路径透明反代（`internal/agent/agent.go` `handleProxy`）。

---

## 1. 名词与边界

| 名称 | 谁定义语义 | 平台知道什么 | 执行路径 |
|---|---|---|---|
| 基线能力 | 平台 | 全部（有专门 UI/业务） | 强类型 `ChannelDriver`（play/ptz/…）+ fuse |
| 自定义能力 | 驱动开发者 | 只知"已注册"（id/title/schema） | 通用 `command` 透传，平台不解析 payload |
| 平台已知事件 | 平台 | 全部（`eventtype` 注册表） | `zws_event` + 可选投影 `zws_alarm` |
| 自定义事件 | 驱动开发者 | 只知基础字段（信封） | `zws_custom_event`（raw 原样，平台不解析） |

**"平台不知道" = 不懂语义，不是"不知道存在"。** 自定义能力/事件也必须在清单登记，平台才能展示、路由、审计、置灰。

## 2. 能力模型改造（声明驱动）

### 2.1 现状问题（为什么现在识别不了"是否支持回放"）
- `protocolDeviceOps("plugin")` 硬编码返回 `play/playback/ptz/snapshot/alarm/subscribe/sync`（`internal/infrastructure/persistence/asset_backfill.go`），与插件实际能力无关。
- `upsertCapabilities` 一律写 `Supported:true`。
- 清单 `capabilities` 只有布防项被读（`eventsub.supportsAlarm`）。
- 结果：设备"声明支持回放"→ 调用不通 → 运行时熔断，**靠失败兜底**。

### 2.2 目标：清单成为唯一事实来源

**manifest 基线能力**（不变，仍为枚举校验）：
```yaml
capabilities: [login, logout, channels, live, ptz, snapshot]   # 只写真正实现并验证过的
```

**能力投影规则**（关键，解决"缺失即放行"的坑）：
- 插件设备投影**全部基线设备级能力**为行，`Supported = (op ∈ manifest.capabilities)`。
- 未声明的基线能力 → `Supported=false` → `checkResourceCap` 明确拒绝（"该通道不支持回放"），**不再靠调用失败**。
- 资源级 `play/snapshot` 亦 `∩ 声明`；`ptz/audio` 继续按 `ptzType/hasAudio`。
- GB/ONVIF 本轮维持现状（各自适配器声明全量），行为不变。

`upsertCapabilities` 签名调整（示意）：
```go
// declared = 该协议/该插件声明支持的能力集合；baseline = 该协议基线全集
supported := declaredSet[op]   // 不再恒 true
```

### 2.3 自定义能力声明
manifest 新增（与 `capabilities` 分开）：
```yaml
custom_capabilities:
  - id: face.push            # ^[a-z][a-z0-9._-]{1,63}$，不得与基线能力重名
    title: 下发人脸
    params_schema: {type: object, properties: {imageUrl:{type:string}, personId:{type:string}}, required:[imageUrl]}
    result_schema: {type: object, properties: {accepted:{type:boolean}}}
```
- `params_schema` / `result_schema` 可选（纯透传时代如无 schema 则平台不校验，仅透传）。
- 校验（`internal/domain/pluginpkg/inspect.go` `validateManifest`）：
  - `id` 匹配 `protoRe` 风格、全局唯一、**不得命中 `capabilitySet`（基线）**；
  - `title` 非空；schema 若存在必须是合法 JSON。

能力表写入：`scope=device`，`Operation=id`（如 `face.push`），`Source="custom"`，`Supported=true`，`Available` 随 fuse。基线 op 与自定义 op 同表，`Source` 区分来源。

## 3. 通用命令透传（`command`）——解决"下发人脸"等自定义能力

### 3.1 插件侧（驱动实现）
```
POST /v1/command
req : { deviceUid, channelId?, cmd, params }        # params 为任意 JSON，平台不解析
resp: { code:"OK", data }                            # data 原样回给平台
```
- 驱动在 `/v1/command` 内按 `cmd` 分派到自己实现；未注册的 cmd 返回 `unsupported`。
- 与现有 envelope 一致（`internal/adapter/ipcplugin/client.go` 的 `envelope`）。

### 3.2 平台侧
```
POST /api/v1/resources/:id/command/:cmd
body: { params: <json> }
```
处理：解析 resource → 取 device/resource 内码 + 协议侧标识（deviceUid/channelId）→ 若 `params_schema` 存在则校验 → 调插件 `/v1/command` → 原样返回 `data`。
- 鉴权：JWT（`RequireMenu`），并校验 resource 归属。
- 审计：写操作日志（who/when/device/channel/cmd，payload 摘要，结果码）。
- fuse：非 `OK` → `SetCapabilityAvailable("device", devID, cmd, false)`；成功 → 恢复 true。
- 实现：`ipcplugin.Client.Command(ctx, deviceUID, channelID, cmd, params) (json.RawMessage, error)`。

### 3.3 基线与自定义的执行分界
- 基线（play/playback/ptz/snapshot/…）：**仍走强类型 driver**（流会话、回放 SSRC、云台归一化、fuse 都在这里）。
- 自定义：走 `command` 透传。
- 二者**声明、能力表、fuse、UI 生成完全相同**——"对齐"的是模型，不是把 play 塞进透传壳。

## 4. 自定义事件（`zws_custom_event`）

### 4.1 路由规则（拆开现有 `other` 耦合）
事件仍走现有 MQTT → `eventingest`，按类型分流：
- `eventtype.IsKnown(eventType)` 命中基线注册表 → `zws_event`（现状）。
- 否则 → `zws_custom_event`（**不再**归一成 `other` 塞进 `zws_event`）。
- 新增 `eventtype.IsKnown`（现有 `Normalize` 会回落 `other`，需先判成员再回落）。

### 4.2 上报信封（平台只约定基础字段，`raw` 原样）
```json
{
  "eventId": "uuid",
  "deviceInternalCode": "D...",
  "channelInternalCode": "C...",
  "channelId": "101",
  "majorType": "access",          // 大类（可缺省=自定义）
  "minorType": "card.open",       // 小类：上报什么就是什么
  "occurTime": 1700000000000,
  "level": "info",
  "imageKey": "optional",
  "raw": { "cardNo": "A1B2", "doorId": 3, "...": "..." }
}
```
- 平台只对基础字段建索引/内码关联；`raw` 原样存，驱动/用户自解析。

### 4.3 表结构 `zws_custom_event`
| 列 | 类型 | 说明 |
|---|---|---|
| id | VARCHAR(36) PK | UUID |
| event_id | VARCHAR(64) UK | 幂等去重 |
| device_internal_code | VARCHAR(32) | 设备内码（索引） |
| channel_internal_code | VARCHAR(32) | 通道内码（索引） |
| device_id / resource_id | VARCHAR(36) | 解析到的统一资产（可空） |
| major_type | VARCHAR(64) | 大类（索引） |
| minor_type | VARCHAR(128) | 小类（索引） |
| occur_time | BIGINT | 毫秒（索引） |
| level | VARCHAR(16) | 级别 |
| image_key / image_url | VARCHAR(512) | 可选 |
| raw_json | LONGTEXT | 原始 payload（含 raw） |
| create_time | VARCHAR(32) | |

### 4.4 接口与菜单
- `GET /api/v1/custom-events?deviceCode=&channelCode=&majorType=&minorType=&start=&end=&page=&count=`
- `GET /api/v1/custom-events/:id`
- `GET /api/v1/custom-events/types`（该设备/插件声明过的 major/minor 去重，供筛选）
- 菜单：「自定义事件」（置于事件中心附近），页面按基础字段列表 + 详情展示 `raw`（折叠，排障用）。
- 开发者业务：按内码/类型/时间拉取，自建表自解析——平台不再侵入。

## 6. 改动点清单（按阶段）

### P1 · 声明驱动（先让"识别能力"成真，不动执行）
- `inspect.go`/`entity.go`：加 `custom_capabilities` 解析与校验。
- `asset_backfill.go`：`protocolDeviceOps` 对 plugin 改为读清单 `capabilities`；未声明基线写 `Supported=false`。
- 接入页能力列（`deviceaccess/service.go`）改为由能力表生成，不再按协议写死。
- 验收：一个只声明 `login/channels/live` 的插件，设备页回放/云台/抓拍按钮**如实置灰**，接口直接拒绝。

### P2 · 通用命令透传（跑通"下发人脸"）
- 插件契约加 `/v1/command`（另出驱动侧开发指南 + Mock 实现）。
- 平台：`ipcplugin.Client.Command` + `POST /api/v1/resources/:id/command/:cmd`（校验/审计/fuse）。
- 自定义能力写入 `zws_capability`（`Source=custom`）。
- 验收：上传含 `custom_capabilities:[face.push]` 的 Mock 插件 → 设备详情出现"下发人脸"→ 调命令 → 驱动 `raw` 原样返回 → 审计留痕。

### P3 · 自定义事件（跑通"刷卡/开门记录"）
- `zws_custom_event` 表 + domain/repo/service/handler/routes + 「自定义事件」菜单页。
- eventingest 按 `IsKnown` 分流；未知类型落自定义表。
- 验收：插件上报 `minorType=card.open` + `raw` → 进自定义表 → 页面可见 → 开发者按内码/类型拉取自建业务。

## 7. 风险与边界
- **兼容**：GB/ONVIF 能力投影本轮不变；仅 plugin 改声明驱动。存量插件若未声明回放/抓拍，P1 后相关按钮会置灰——这是**如实暴露**，需在发布说明提示。
- **透传≠不设防**：platform 仍做鉴权、resource 归属校验、超时、审计、fuse；"透传"仅指不解析 payload 语义。
- **schema 可选**：无 schema 时纯透传；有 schema 平台按其校验（只校验不解释语义）。
- **事件不串库**：自定义事件绝不写入 `zws_event`/`zws_alarm`，保持边界清晰。
- **不重复造字典**：`custom_capabilities.id` 强制不得与基线能力重名，避免同一能力两套语义。
